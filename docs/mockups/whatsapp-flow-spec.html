02

Getting in — enrolment

A number is either enrolled to a named staff member or it is a stranger. There is no in-between, and strangers get nothing.

M
Macavation
Business account
ADMIN CLICKS "SEND CODE"
Hi Anli. Your Macavation code is 418 302.

Send it back to me to finish setting up. It expires in 15 minutes. 10:02
41830210:03 ✓✓
Thanks Anli, this number is now enrolled.

Text HELP any time to see what I can do, or just say hello for the menu. 10:03

The admin is standing next to them when this happens.

IN-1Admin issues a code
Where
Portal → Users → edit a person → Send enrolment code
Needs
The admin.users.manage permission, re-checked on the server
Code
Six digits, expires in 15 minutes, limited attempts. Never shown in the portal and never logged — it only ever exists on their handset
State
Built on the dev branch
IN-2They send it back
Match
Exactly six digits, nothing else in the message
Success
Number is bound to that person, permanently and uniquely. One number can never belong to two people
Failure
Total silence. Wrong code, expired code, no code pending — all answer nothing
State
Built and live
Why silence on a bad code. Replying "wrong code" to any number that happens to text six digits confirms the line is live and leaks that an enrolment is in progress. The person actually enrolling is standing with the admin who issued it, so they just say "nothing came through" and get a fresh one. Nobody else learns anything.
The catch today. That first message is unprompted — so it needs an approved template, and there isn't one. Right now the code can only be delivered if the person messaged the number in the last 24 hours, which rather defeats the purpose. The enrolment template is the fourth one to submit.

What a stranger gets

Silence. Not an error, not a "you're not registered" — nothing at all. The line never confirms it exists to a number that has no business on it.
Still recorded. The message is stored and logged, so you can see in the portal that an unknown number tried and decide whether to enrol them.
The one exception worth adding. Report recipients who aren't staff — a shareholder, say — should be able to say stop and be obeyed, even unenrolled. Opting out must never require an account.

Nothing new to maintain. The gate is the same permission that shows or hides the area in the portal sidebar. Give someone access to stock in the portal and it appears on their phone; take it away and it vanishes. There is no second list to keep in step.
Ten rows is the ceiling and titles cap at 24 characters — a hard Meta limit on the tappable sheet. Eight items leaves room for two more before this has to become two levels.
The one change needed. Today an unrecognised word gets a list of verbs to type. It should open this menu instead. Hello, hi, start, menu, 0, 99, ? and an empty message already do.

Typed numbers match the position in your own filtered list, so "3" always means the third row you were actually shown. Someone who can't see stock has a different list, and their 3 is a different thing — correctly.

Cheaper than it looks. The pause date already has a column and the daily sender already respects it. The function that changes a subscription from a phone number is already written and granted — nothing has ever called it. This branch is mostly wiring.

Stop works from anywhere. The word stop is obeyed at any point in any conversation, even mid-way through something else, even from a number that isn't enrolled. It is never behind a menu.

Step 3 — done, and say what's left

AL-1Permission is checked twice
Once
When they ask — no resolve option appears at all if their role can't resolve alerts
Again
At the moment they confirm, on the server. A permission removed in between is honoured
State
Built on the dev branch
AL-2A pending request expires
Held
One at a time, per person. Asking for something else replaces it
Expiry

Cancel
NO, N or CANCEL — "Cancelled, nothing was saved"
What gets pushed, and what doesn't. Critical alerts go out unprompted to everyone who opted in. Warnings go only to people who asked for warnings. Info never leaves the portal. On top of that: the same alert is never sent twice, and there's a daily cap per person. Meta scores the number on how people react to it, and a poor score cuts how many messages you may send of any kind — so alert noise would degrade the reports too.

08

Changing data — the confirm rule

One rule, applied to every request that writes anything to the business: say back what you understood, and wait.

The rule

  1. Understand it. Work out exactly what they asked for.
  2. Say it back. In full, in plain words, with the specific thing named — not "confirm this change?"
  3. Wait. Nothing is written yet.
  4. YES writes it and confirms what was done, with the time. NO discards it and says nothing was saved.
  5. Re-check permission at the moment of writing, not at the moment of asking.
Reading never confirms. Every menu item in section 4 answers straight away.
Good — names the thing
Resolve Low stock: Protein, raised 16 Aug? [ Yes, resolve ] [ Cancel ]
Bad — could be anything
Are you sure you want to continue? [ Yes ] [ No ]
Why it matters more here than in a browser. People reply to WhatsApp one-handed, walking, half-reading. The confirmation is the only chance to catch a misread — so it has to carry enough detail to be worth reading.
Today there is exactly one of these — resolving an alert, on the dev branch. The pattern and the plumbing behind it are built and waiting; anything added later registers itself and inherits the whole flow.

09

When things go wrong

Every one of these will happen. What matters is that none of them leave someone stuck or told something untrue.

What happensThey seeWhy
They tap an old menu
after a new version deployed		 "That option is no longer available. Reply 99 for the menu." Old messages stay in the chat forever and stay tappable. Treated as stale, not as an error.
Their role changed
mid-conversation		 The menu, re-filtered. The item is simply gone. Permission is read fresh every time, never cached in the conversation.
Their role has nothing enabled "Your role doesn't have access to any of the WhatsApp reports yet. Ask an administrator to enable the areas you need." An unreadable permission table must fail to an empty menu, never a full one.
The tappable sheet won't render
old handset, odd client		 The same menu as numbered text. Automatic. Typed numbers match the same positions, so nothing is lost.
A figure is missing A dash, and a line saying why. Never a zero. "0 weeks cover" and "cover unknown" mean opposite things.
They message outside 24h
and we owe them something		 A template, not free text. Free text sent to a shut window is accepted and then silently dropped — it looks sent and never arrives. The commonest way this goes wrong invisibly.
A template isn't approved Nothing. Meta reports "template not found", which says nothing about approval. Check the template's real status before blaming the sender.
They opted out Nothing, ever, until they ask. Checked immediately before every send. No exception for "important".
A stranger messages Nothing. Recorded so you can see it in the portal, but never answered.
Something breaks our side Nothing. There are no retries — a message we fail to handle is gone for good. So it is stored before anything else is attempted, and failures are logged loudly with the message id.
The failure to design against. A message sent to a closed window is accepted by everything in the chain and then quietly dropped by Meta. No error, no bounce — it simply never arrives. That is why the portal must show which mode a send is about to use before the button is pressed, and why every delivery is recorded with its receipt.

Constraints that don't change and shouldn't be argued with mid-build. Most are Meta's; two are house rules across every Customapp WhatsApp product.

Never introduce another key for back or menu, and never use the legacy 9. Someone who learns this on one Customapp product is right on all of them.
