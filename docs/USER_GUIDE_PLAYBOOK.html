1. How the help system works

The user guide is a single HTML file (WebPortal/help/user-guide-v2.html) that serves two purposes:

ModeHow it's openedWhat the user sees
Single-section In-app Help button links to user-guide-v2.html#section-id Only that one section, with a "Full user guide" link at the top
Full guide User clicks "Full user guide" or opens user-guide-v2.html?full=1 All sections in order, table of contents, SVG diagrams, chapter dividers

The JS (help-shell.js) handles the toggle. You don't need a build step, static site generator, or framework. Everything is vanilla HTML, CSS, and JS.

Golden rule: Every deep-linkable screen in the app must have a matching <section> in the guide with the correct id and data-guide-id.

3. Anatomy of a guide section

Major module section (appears in TOC)

<!-- The id MUST match the route name or data-guide-id used by the app -->
<section id="grower-intake-grid"
         class="guide-section"
         data-guide-id="grower-intake-grid">

  <h2>Grower Intake</h2>

  <!-- Lead: 1-2 sentences. What is this and why does it exist? -->
  <p class="guide-lead">This is where macadamia nuts arrive...</p>

  <!-- How: practical context. When to use it, what to watch for. -->
  <p class="guide-how">Work delivery by delivery. The flow is...</p>

  <!-- Steps: numbered, action-oriented -->
  <h3 class="guide-subhead">How to use it</h3>
  <ol class="guide-page-steps">
    <li>Open <strong>Grower Intake</strong> from the sidebar.</li>
    <li>Switch between <strong>Board</strong> and <strong>Table</strong> view.</li>
    <li>...</li>
  </ol>

  <!-- Optional: tip callout -->
  <div class="guide-tip"><strong>Tip:</strong> Use Export for...</div>

  <!-- Screenshot (auto-generated by Playwright) -->
  <figure class="guide-shot">
    <img src="./assets/screenshots/grower-intake-grid.png"
         width="1200" height="675" alt="Grower Intake" loading="lazy" />
  </figure>
</section>

Modal / subsection (hidden from TOC)

<section id="modal-grower-receiving-checklist"
         class="guide-section"
         data-guide-id="modal-grower-receiving-checklist"
         data-toc="0">

  <h2>Receiving checklist (grower)</h2>
  <p class="guide-lead">This is Stage 1 of intake...</p>

  <ol class="guide-page-steps">
    <li>Open from a batch card or row actions.</li>
    <li>Complete every line item.</li>
    <li>Save.</li>
  </ol>
</section>

Required attributes

AttributePurposeRequired?
idDeep-link target. Must match the app's route name or help-button anchor.Always
class="guide-section"JS uses this to find all sections for TOC building, show/hide logic.Always
data-guide-idShould match id. Used by the app for contextual help lookups.Always
data-toc="0"Excludes the section from the table of contents. Still visible in full mode, still deep-linkable.Modals & subsections only
data-exclude-from-full-guide="1"Hides from TOC and from full guide view entirely. Used for test management sections.Internal/test sections only

4. Writing tone & voice

The guide is read by factory floor operators and office managers — not developers. Write like you're explaining it to a smart colleague on their first day.

PrincipleWhat it means in practice
Use "you""You'll see the batch appear on the board" — not "The batch will appear on the board for the user."
Short sentencesMax 20 words per sentence where possible. Break long thoughts into two.
Active voice"Click Save" — not "The Save button should be clicked."
Concrete"Open CRM → NIS Suppliers tab" — not "Navigate to the appropriate contact management section."
Explain why, not just what"Keep contacts accurate because dispatch paperwork pulls from here" — not just "Maintain contacts."
No jargon without definitionFirst use of NIS, FFA, GRV etc. should be explained or linked to the glossary.
Workflow-firstDescribe the process, mention key fields, skip obvious form labels.

5. Do / Don't examples

Lead paragraph

"This is where macadamia nuts arrive. When a grower delivers NIS, you log the delivery, run through a receiving checklist, and create a kernel batch."
"Dialog opened from the related module. Complete required fields (marked), then save. Use Cancel or the close button to dismiss without saving."

Steps

"For each new delivery: start with the Receiving checklist — it's Stage 1 and unlocks everything else."
"The user should complete the receiving checklist form by filling in all required fields and submitting the form."

Tips

"If quantities don't match, fix it in Stock Management. Forcing mismatches through dispatch creates downstream problems."
"Ensure data integrity by verifying quantities prior to dispatch operations."

Modal descriptions

"The job card captures production detail — styles, yields, equipment. Fill it per your factory standard."
"Dialog opened from the related module. Complete required fields (marked), then save."

6. Adding a section for a new module

When you build a new module, add its guide section in the same commit. Here's where to put it and what to write:

  1. Find the right chapter. Sections are grouped by workflow:
    ChapterWhat goes here
    Your daily viewDashboards, My Day
    Contacts (CRM)CRM tabs and contact types
    Kernel streamGrower intake → production → stock → dispatch
    Oil & protein streamSupplier intake → production → stock → dispatch
    Quality & traceabilityQA, batch journey
    Business & reportingSales, finance
    Documents & integrationsDocs, Palladium, data import
    AdministrationUsers, roles, permissions, features, admin
  2. Add the section in the HTML, inside the right chapter, in workflow order.
  3. Write the content following the anatomy in section 3 above:
    • Lead paragraph — what is it, why does it exist (1-2 sentences)
    • How paragraph — practical context (1-2 sentences)
    • "How to use it" steps — 4-6 numbered actions
    • Optional tip callout
    • Screenshot reference
  4. Add the route to appRouteConfig.json and the Help button to your module HTML: 
    <a href="/help/user-guide-v2.html#your-module-grid"
   target="_blank" class="btn btn-sm btn-outline-secondary">
  <i class="bi bi-question-circle"></i> Help
</a>
  5. Add a glossary entry if your module introduces new terms.

7. Adding a modal subsection

Not every modal needs its own section. Use this decision tree:

Modal typeWhat to do
Simple Add/Edit form (name, description, save)Skip it. The parent section's steps should mention it in passing.
Multi-step dialog (checklist, dispatch form, production stages)Add a subsection with data-toc="0". Write 1-2 lines of lead + 3-4 steps.
Read-only view dialog (job card view, batch history)Add a minimal subsection — 1 line of lead, no steps needed.

Place the modal section immediately after its parent module section in the HTML. This keeps related content together when reading the source.

8. SVG diagram conventions

Inline SVGs are used for workflow diagrams. Follow these rules:

RuleDetail
Colour schemeBoxes: #e8f0ec (green) or #e8edf0 (blue-green for oil). Borders: #2d4a3e. Arrows: #4a6b5c. Text: #1a2e26. Sub-text: #5a6b63.
Fontsystem-ui, "Segoe UI", sans-serif — matches the guide body text.
Clickable boxesWrap in <a href="#section-id"> with a <title> for accessibility.
Hover stateAdd :hover rule to lighten the box fill.
ContainerWrap the SVG in <div class="guide-flow"> — this adds the white card, border, and horizontal scroll on narrow screens.
Hidden in single modeThe CSS hides .guide-flow when viewing a single section.

10. JS behaviour summary

You shouldn't need to edit help-shell.js when adding content. But here's what it does so you understand the constraints:

FeatureHow it works
TOC generationOn load, finds all section.guide-section[id] elements. Skips those with data-exclude-from-full-guide="1" or data-toc="0". Builds a <ul> of anchor links.
Single/full toggleIf the URL has a #hash pointing to a .guide-section (without ?full=1), only that section is shown. Everything else is hidden.
Full guide linkDetects the current filename dynamically — works for both index.html and user-guide-v2.html.
Missing screenshotsIf an image in .guide-shot fails to load, the figure gets .is-missing and is hidden.
Back to topShows #back-to-top after 400px scroll. Hidden in single-section mode and when the element doesn't exist.

11. Developer checklist

Use this every time you add or change a user-facing module:

  1. Add the guide section in user-guide-v2.html inside the correct chapter.
    • Use the section anatomy from section 3.
    • Set id and data-guide-id to match the app route.
  2. Write in the right tone. Re-read the Do / Don't section if unsure.
    • Lead: what is it, why does it matter?
    • Steps: what does the user actually do? (4-6 steps)
    • Tip: anything non-obvious that saves time or prevents mistakes?
  3. Add modal subsections only for complex dialogs. Use data-toc="0".
  4. Add a Help button in your module HTML that links to #your-section-id.
  5. Add glossary entries for any new terms (NIS, FFA, etc.).
  6. Add the screenshot filename so Playwright captures it: ./assets/screenshots/your-module-grid.png.
  7. Update an SVG diagram if your module adds a new step to the kernel or oil stream flow.
  8. Commit the guide update in the same commit as the module code. Don't defer it.
  9. Test both modes:
    • Open user-guide-v2.html#your-section-id — does it show just your section?
    • Open user-guide-v2.html?full=1 — does it appear in the right place in the TOC?
Remember: Documentation that ships with the code is documentation that stays current. If it's not in the commit, it doesn't exist.
